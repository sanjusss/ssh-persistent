# 无 `scp` 环境下的文件传输研究

本页记录接入前的设计与原型验证结果。方案现已接入 `push`、`pull`；实际参数与限制以[文件传输说明](transfers.md)为准。原型在临时目录运行，研究记录不包含真实主机名、账号或凭据。

## 推荐路径

| 连接能力 | 推荐方式 | 远端依赖 | 编码后的大小 |
| --- | --- | --- | --- |
| `jump`，允许直接执行远程命令 | 无终端的 SSH 二进制流 | `cat` 等文件读写工具 | 原大小 |
| `shell`，只有交互终端，提供 `base64` | 分块 `base64` 传输 | `base64` 编码与解码工具 | 约 1.33 倍 |
| 有 Python 或 `OpenSSL`，但无 `base64` 命令 | 使用其 `base64` 功能 | 对应解释器或工具 | 约 1.33 倍 |
| 缺少上述工具 | 上传用 `printf` 八进制转义，下载用 `od` 十六进制输出 | shell 的 `printf`、`od` 等基础工具 | 上传约 5 倍；下载约 2 倍，另有空白分隔符 |

`base64` 将二进制数据转换为可打印文本；每 3 个原始字节对应 4 个字符。它适合穿过当前终端输出的文本清理过程。`GNU` 实现默认按 76 个字符换行，接收端应允许这些换行。见 [编码工具官方文档](https://www.gnu.org/software/coreutils/manual/html_node/base64-invocation.html)。

普通十六进制每字节需要 2 个字符。八进制方案使用 `\0ddd`，每字节需要 5 个字符，可直接通过 `printf '%b'` 写入文件。已在本地 `/bin/sh` 中验证全部 256 种字节，包括 零字节、回车、换行和终端控制字节。

直连模式优先省去编码。`OpenSSH` 明确支持通过不分配伪终端的会话可靠传输二进制数据，使用 `ssh -T` 固定这一行为。见 [SSH 官方手册](https://man.openbsd.org/ssh)。

## 对现有实现的影响

- `jump_exec()` 使用 `-n` 和空标准输入。新的二进制传输函数需要单独连接输入输出流，保留现有普通命令的行为。
- `shell` 会话已经登录到最终目标。编码后的数据可沿这条连接直接送达目标，不需要中转机再次运行 `scp`，也不需要 `[local]` 或 `staging`。
- `clean_output()` 会解码文本、删除回车和颜色控制码；输出缓冲超过约 200 万字节 时还会截断。原始二进制不能通过这个接口返回，下载必须编码并分块。
- `_stage_command()` 使用 shell 变量还原命令。文件数据应由解码器直接写入文件，避免通过 shell 变量保存含 零字节 的二进制。
- `do_exec()` 在断线后会重试一次。若每块直接追加到同一文件，重试可能重复写入数据；块写入必须支持安全重试。
- Windows 启动器已取消对 `scp` 的无条件检查。

### 分块大小与现有命令通道

现有 `PtySession.exec()` 会对较长命令再次进行八进制编码。直接发送很长的 `base64` 字符串会增加传输量和确认次数。

本地测量了单个上传命令实际向伪终端写入的数据，包含执行标记和确认命令：

| 原始块大小 | Base64 字符数 | 实际写入字节 | 写入次数 |
| --- | --- | --- | --- |
| 768 字节 | 1024 | 1171 | 1 |
| 1024 字节 | 1368 | 1515 | 1 |
| 4096 字节 | 5464 | 30805 | 23 |

这些数值来自本次原型使用的短路径，路径长度变化会影响结果。原型选择每块 768 字节。正式实现应按完整命令编码后的长度计算块大小，避免意外触发第二次编码；长期可增加专门的数据传输接口。

上传和下载可使用不同块大小。下载命令很短，编码输出可按较大的块读取，但每块必须明显小于现有输出缓冲上限。

## 传输协议建议

1. 探测目标实际可用的编码、解码、分块读取和校验工具，并用已知样本验证。不同 `base64` 实现的选项不能一概而论。
2. 在目标目录所在文件系统创建权限为 `700` 的独立临时目录，分配本次传输的标识。
3. 为每块记录编号、偏移和预期长度。每块写入独立临时文件，成功后改名为对应块文件；重发同一块时覆盖该块，避免追加重复内容。
4. 合并各块后，核对总字节数和 `SHA-256`，即用于核对完整性的文件摘要。校验通过后，再将文件改名到最终目标。
5. 下载按明确偏移读取并严格解码；本地先写临时文件，完成全部校验后再替换目标。若源文件在下载期间变化，应报错或使用一致的快照。
6. 最终完成操作也需支持重试。改名已经成功但确认丢失时，应核对目标文件及传输标识，避免把成功误报为失败。
7. 成功、失败和取消都要清理本次临时文件。彻底断线时，应在重新连接后清理已记录的目录；不能只依赖客户端的退出处理。

临时文件与最终目标应位于同一文件系统，避免跨文件系统移动失去原子替换效果。没有校验工具时，可以考虑下载完整文件进行比对；不能把“收到成功回复”等同于内容一致。

`base64` 并不提供额外保密性，连接仍依靠 SSH 加密。终端审计和调试日志可能保留编码后的文件内容，应避免把这些内容打印到助手回复或普通进度日志中。

## 工具选择

- 原生 `base64`：优先探测并验证编码与解码命令。下载时移除协议允许的空白后，在本地严格解码。
- `OpenSSL`：本地已验证 `openssl base64 -d -A` 能解码无换行的小块。官方文档对大文件使用 `-A` 有限制说明，因此应继续分块。见 [工具官方文档](https://docs.openssl.org/3.5/man1/openssl-enc/)。
- Python：提供标准库 `base64`，适合已安装 Python 的目标；需要使用二进制文件接口。不能假设远端具备本机所要求的 Python 环境。见 [Python 文档](https://docs.python.org/3/library/base64.html)。
- `printf` 与 `od`：本地原型在隐藏 `scp` 和 `base64` 的工具路径中验证了上传、下载。该方案依赖较少，但传输量和往返次数较大。
- `xxd`：本地已验证十六进制解码可行；它增加一个远端工具依赖，优先级低于上述方案。

## 验证范围

本地原型覆盖了空文件、1～2 字节文件、全部字节值、零字节、无效 `UTF-8` 字节、回车换行和终端控制字节。文件名包含中文、空格、单引号、美元符号和分号。

上传时故意重发第一块，验证结果没有重复内容；另一次故意改变一个数据字节，验证摘要不一致时保留原目标文件。

### 真实连接验证

使用已有连接配置验证了直连、堡垒机和多跳终端。所有传输操作均未调用 `scp`；没有卸载或修改服务器上的工具。测量不含首次登录，编码方案的耗时包含分块、校验及重复块测试。

| 方式 | 文件大小 | 上传与下载总耗时 | 结果 |
| --- | --- | --- | --- |
| 直连 SSH 二进制流 | 262144 字节 | 约 0.44 秒 | 内容及摘要一致 |
| 直连命令通道，`base64` | 2058 字节 | 约 2.40 秒 | 内容及摘要一致 |
| 堡垒机终端，`base64` | 2058 字节 | 约 16.88 秒 | 内容及摘要一致 |
| 多跳终端，`base64` | 2058 字节 | 约 16.82 秒 | 内容及摘要一致 |
| 堡垒机终端，八进制上传与 `od` 下载 | 2058 字节 | 约 22.90 秒 | 内容及摘要一致 |
| 多跳终端，八进制上传与 `od` 下载 | 2058 字节 | 约 22.86 秒 | 内容及摘要一致 |

编码原型一次往返分别执行了 17 条和 23 条远端命令。上述终端环境每条命令约需 1 秒，固定往返开销占主导。这些数据只代表本次测试，不能当作不同网络或服务器的性能保证。小文件可以作为应急传输方式，大文件需要专门的连续收发接口或其他可用通道。

重复块和内容破坏测试在三类真实连接中均通过。实验也确认，共享直连连接被其他任务关闭时，传输会中断；正式实现需要明确连接归属和失败清理。本次远端测试文件及专用终端会话已清理。

原型仅验证普通文件内容。目录递归、权限与时间戳保留、符号链接策略、跨进程恢复和不同操作系统的工具兼容性尚未完成正式实现。

## 接入方式建议

为 `push`、`pull` 增加传输方式选择，保留现有 `scp` 功能。自动模式先探测能力，再选择直连二进制流或终端编码方案。权限不足、路径错误和磁盘空间不足应直接报告，不能一律解释成“缺少 `scp`”而改用另一种方式。

首次接入以单个普通文件为范围。更大的文件通常由终端往返延迟限制速度，编码体积只是一部分开销；不宜仅凭 `base64` 的 33% 膨胀率估算传输时间。
